# 多國語系維護指南

ZeroLightRokid Desktop 支援 **14 個語系**，與手機端 App
（`rokid_root/android/app-phone`）的語系清單一致，術語也沿用該 App 的既有翻譯。

## 1. 資料流

```
tools/i18n_master.json          ← 唯一真相來源（14 語系 × 241 字串）
        │
        │  tools/gen_i18n.py         驗證 + 產生
        ▼
src/i18n_strings.h              ← 自動產生，勿手改
        │
        │  #include
        ▼
src/i18n.h                      ← 執行期：偵測 / 查表 / 字型 / RTL
        │
        ▼
src/zero_light_desktop.c        ← UI 以 T(STR_xxx) / Tf(STR_xxx, args) 取字串
```

**永遠不要直接編輯 `src/i18n_strings.h`** —— 它每次建置都會被重新產生。

| 2 | `en` | English | Segoe UI | 0x09 |
| 3 | `ja` | 日本語 | Yu Gothic UI | 0x11 |
| 4 | `ko` | 한국어 | Malgun Gothic | 0x12 |
| 5 | `fr` | Français | Segoe UI | 0x0C |
| 6 | `de` | Deutsch | Segoe UI | 0x07 |
| 7 | `es` | Español | Segoe UI | 0x0A |

## 3. 字串格式規範

| 寫法 | 意義 |
|---|---|
| `%ls` | 寬字串引數（`wchar_t *`） |
| `%d` / `%02d` / `%04d` | 整數引數 |
| `%%` | 輸出一個字面百分比符號 |
| `\r\n` | 對話框中的換行 |

- 一律使用 **`%ls`**，不要用 `%s` 或 `%hs`：MinGW 的 ANSI stdio 與 MSVC 對
  「寬 printf 中的 `%s`」採不同慣例，`%ls` 在兩者皆明確代表寬字串。
- 同一個 key 在**所有語系**的格式符必須完全一致（數量、順序、長度修飾詞）。
  `gen_i18n.py` 會驗證，不一致就建置失敗。
- 落單的 `%`（既非格式符也非 `%%`）會被驗證器擋下 —— 它在執行期會讓
  `vswprintf` 讀取不存在的引數，是很危險的錯誤。

## 4. 修改既有翻譯

1. 編輯 `tools/i18n_master.json` 中對應 key 的對應語系欄位。
2. 重新產生並驗證：

```bash
python3 tools/gen_i18n.py
```

3. 重新建置。

## 5. 新增一個語系

1. 在 `tools/i18n_master.json` 的 `locales` 陣列加入一項：

```json
{ "code": "it", "name": "Italiano", "english": "Italian",
  "font": "Segoe UI", "rtl": false, "win_primary": 16, "win_sublang": -1 }
```

   `win_primary` 是 Win32 LANGID 的主要語言 ID（`LANGID & 0x3FF`）；
   若同一語言需要區分地區（如中文），再給 `win_sublang`（`(LANGID >> 10) & 0x3F`）。

2. 為該語系補上全部字串。可先只填 `en`，再執行
   `python3 tools/i18n_apply.py` 讓缺漏自動以英文暫代（確保隨時可編譯），
   之後再逐步取代。

3. 若要交由翻譯者處理，請提供 `tools/i18n_glossary.md`（術語基準）與
   `tools/i18n_master.json`，翻譯片段格式為：

```json
{ "it": { "BTN_APPLY": "Applica", "BTN_CANCEL": "Annulla" } }
```

4. 併入片段並驗證：

```bash
python3 tools/i18n_apply.py it.json
python3 tools/gen_i18n.py
python3 tools/i18n_apply.py --status     # 查看各語系完成度
```

5. 若新語系需要專屬後備字型鏈，在 `src/i18n.h` 的 `i18n_make_font()`
   中加入對應的 `case`。

## 6. 驗證

### 產生階段（資料正確性）

```bash
python3 tools/gen_i18n.py --check
```

檢查：每個 key × 每個語系皆非空、格式符跨語系一致、無非法控制字元、
locale 代碼與 LANGID 唯一、**`en` 基準不含非 ASCII**（防止「誤把中文寫進
英文欄位」這類資料損毀擴散到所有以英文暫代的語系）。

### 建置後（執行檔正確性）

```bash
python3 tools/verify_exe.py zero_light_desktop.exe
```

直接從 PE 的 `.text` / `.data` / `.rdata` 取出位元組，逐字串比對 UTF-16LE
編碼，確認**全部 3,374 筆翻譯真的被編進執行檔**（可抓出編譯期截斷、
字串合併等問題），並確認阿拉伯文不含 bidi 控制字元。

## 7. 已知的「刻意相同」字串

以下 key 在所有語系都刻意與英文相同（純命令／檔名／路徑，翻譯反而有害）：

- `CMD_DEFAULT` — `id; getenforce`
- `LOG_LASTDONE` — `--- last.done ---`
- `LOG_OTALOCK_SUSPEND` — `  pm suspend %ls`
- `LOG_START_ADB` — `[i] adb = %ls`

因此 `i18n_apply.py --status` 會把這些計為「待譯」，完成度不會顯示 100%。
這是正常的，不是缺漏。

## 8. 特殊語系注意事項

- **阿拉伯文（`ar`）**：**不得**在字串中插入 bidi 控制字元
  （U+200E/200F/202A–202E/2066–2069）。方向性由 `WS_EX_LAYOUTRTL` 處理，
  內嵌控制字元反而會破壞紀錄輸出。`verify_exe.py` 會檢查。
  另因拉丁字元（`root`、`pm suspend` 等）會出現在阿拉伯文句子中，
  翻譯時盡量讓拉丁詞落在句首或句尾，排版較穩定。
- **法文（`fr`）**：冒號前用窄不斷行空格（U+202F），引號用 `« »`。
  例外：`LOG_START_TIME` 的 `%02d:%02d:%02d` 是機器時間戳，保持半形冒號。
- **泰文（`th`）**：詞間通常不加空格，只在子句之間加。
- **中日韓**：`ja` 用 `「」`，`zh-TW` 用全形 `（）：／`，`ko` 用 `( )`。
- 技術名詞一律保留拉丁寫法：`root`、`ghostlock`、`SELinux`、`Shizuku`、
  `exploit`、`adb`、`OTA`、`WiFi`、`Bluetooth`、`Android`、`APK`、`LED`、
  `AUTO`、`TCP`、`USB`、`uid=0`、`Permissive`、`Enforcing`，以及所有
  檔名／路徑／命令。
