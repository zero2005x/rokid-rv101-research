## EXEC_CMD result

With a real TA loaded, the EXEC branch is fully exercised and **returns the TA's raw output bytes verbatim, without any framing, status word, or error channel**:

- `0x00010001` (+4 B payload) → TA dispatch OK, **0-byte payload** → server sends **0 bytes**, logcat `ret:300e`.
- `0x00010002` (+4 B payload, applet-info) → **`32 35 2e 30 35 2e 30 36 2e 30 31` = `"25.05.06.01"`, 11 bytes** on the wire.

So on the wire, *"success"* is signalled by bytes arriving at all; the length is entirely TA-determined (the service's 20480-byte output buffer is truncated to the TA-reported length). An empty TA answer is indistinguishable on the wire from a dispatch error — hence logcat remains the only channel that separates "TA returned nothing" (`300e`) from "no TA loaded" (`300c`).

## Adjudication

**Yes — the "successful EXEC_CMD path" is now exercised on the live device**, and it required a real signed TA loaded first, exactly as predicted.

1. **`LOAD_TA` can succeed** (`"load ta succeed"`, 15 B). The previous "LOAD_TA never succeeds / no TA can be loaded" conclusion (§5.2 S8, S10) was an artifact of the *only* files tested being non-TA inputs (missing file, `/system/bin/sh`). A genuine single-file signed QSEE applet ELF from `/vendor/firmware_mnt/image/` loads on the first attempt.
2. **The missing `qseeproxydaemon` is a red herring** for this path: init *still* cannot start it (`dmesg`), yet the load succeeded. Failure code `300a` was about the *TA image format*, not about a missing QSEE listener.
3. **The intended TA is `smcinvoke_gate_ta64.mbn`** — GateServiced is an SMCInvoke-gate client (`ISMCIGate_*`), and its `run_load_ta` internally drives the TA's applet-info command `0x10002` and parses `ta version` (`25.05.06.01`). Loading it is the service's designed behaviour, not an out-of-band abuse.
4. **What a successful EXEC_CMD returns:** the TA's raw output, byte-for-byte (`"25.05.06.01"`, 11 B). `0x00010002` is the applet-info query; `0x00010001` is accepted and dispatched but yields no data. Error paths still send nothing and are visible only in logcat (`300c` = no TA loaded, `300e` = TA returned 0 bytes).
5. **Single-TA semantics confirmed:** the loaded flag is service-global and persists across client connections (`cmd_dispatch, times = 88` on the load connection, then EXEC succeeded from a *different* connection); `UNLOAD_TA` clears it and restores `300c`.

## Residual risk

- **TA lifecycle:** loaded once, then explicitly unloaded; `dmesg` shows the smcinvoke server released cleanly (`server id : 23 state to defunct`) with **no panic, TZ fault, or watchdog line**.
- **Nothing persisted:** no `/data/misc/qsee` and no `/data/vendor/qsee` were created; the TA's `dtx_sfs_*`/crypto commands were never invoked (only the read-only applet-info query).
- **Files:** the staged TA copies (`/data/local/tmp/ta_*.mbn`, 2.6 MB of vendor TA blobs) were **deleted**. Untouched pre-existing artifacts left in place: `/data/local/tmp/GateServiced.root` (parent agent's pull), `.greq`/`.gresp` (harness scratch).
- **Not probed (deliberately out of scope):** the TA's mutating commands (`base_ta_func_write/delete`, `dtx_sfs_*`, `dtx_rsa_key_generate_path`, `dtx_get_heap_usage`, …) and the `dispatch_antdtx` command space. **These are the real attack surface** — a local client that can `LOAD_TA` this TA and then reach its crypto/file commands.
- **Standing finding (unchanged, now stronger):** `GateServiced:8341` is an **unauthenticated local root TEE loader** — any local app that can reach `127.0.0.1:8341` can load a named TA image from any path GateServiced can read and then issue EXEC commands to it. This work only proved the benign form of that path.
