## 3. Adjudication

### (a) "all commands return 300c" vs "timeout means error" → **both are correct; they are two observation channels of the same event.**
Not a contradiction. `300c` is an **internal return code logged to logcat**, never transmitted:
- Every failing probe (P2–P6) produced **zero TCP bytes** while the server **kept the connection open** (`ESTABLISHED` at sample time) — i.e. the client sees a **timeout**, not data, not `300c`, not a close.
- The same instant produced the logcat line `[GATE CA][ERRO][handle_client][59]:"cmd_dispatch failed, ret:300c"`.

So: wire truth = **response only on success; timeout = error** (the playbook's own line 166:
*"handle_client only calls sendto() when cmd_dispatch returns 0 … response = success, timeout = error"*).
Log truth = the specific error code, e.g. `300c`. The phrase *"all commands return 300c"* is
**overbroad in two ways**, both now measured:
1. It is a **logcat** fact, not a wire fact — nothing is sent over TCP on error.
2. It is **not "all" commands**: `UNLOAD_TA` (P1) **succeeds and returns data** on the wire, and
   `LOAD_TA` failures return **`300a`**, not `300c`. `300c` is specific to the EXEC branch
   (`run_exec_cmd_ta`: `TA is not already loaded`, logcat line 234).

### (b) capability set "almost all bits (`000001ffffffffff`)" vs "four named caps" → **category error; the two are different domains and are not comparable.**
`000001ffffffffff` is a **Linux kernel process-credential mask**, not a GateServiced protocol
capability advertisement. Measured directly:
```
/proc/1792/status   (GateServiced, uid 0)
  Uid:    0 0 0 0
  CapPrm: 000001ffffffffff
  CapEff: 000001ffffffffff
  CapBnd: 000001ffffffffff
/proc/self/status   (adb shell, uid 2000)
  CapEff: 0000000000000000
  CapBnd: 00000000000000c0
```
The mask is a **per-process** attribute that varies by process (root GateServiced = 41 bits;
shell = 0 effective) and is read from `/proc/<pid>/status` — a kernel interface, not a
GateServiced query. The "four named caps" describe the service's **protocol vocabulary**
entirely. Empirically the wire vocabulary is **exactly three branches** (P1, P4–P6):
| cmd_id | Branch | Evidence |
|---|---|---|
| `0x00010003` | LOAD_TA | logcat `load ta called` (P5, P6) |
| `0x00010004` | UNLOAD_TA | logcat `unload ta called`, success reply (P1) |
| *any other value* | EXEC_CMD | P2 `cmd_id = 1`, P3 `deadbeef`, P4 `10001` all → `run_exec_cmd_ta` → `300c` |
The fourth "cap" in the RE report is the **internal** TA-info query (`get_ta_version` /
`dtxGetAppletInfo`, load cmd `0x1001`) invoked *inside* `run_load_ta`, which is **not
client-reachable** over TCP. So both statements are true in their own domain; the
contradiction dissolves once "capability" is disambiguated (kernel credentials vs wire commands).

### Bonus: playbook claim "TA never loads; … qseeproxydaemon missing" → **partly confirmed, refined.**
- `qseeproxydaemon` **is genuinely absent**: `ls` fails at both `/system/vendor/bin/` and `/vendor/bin/`.
- `LOAD_TA` **does not succeed** (no `load ta succeed` in any probe; P5/P6 → `300a`).
- But the failure code is **`300a`**, and the playbook's error table assigns `3001`
  (GENERAL_ERROR / `get_file_size` returned 0) to a missing file. On this live build a missing
  file yields **`300a`** via `load_app` → `run_load_ta` — the static error table is **wrong /
  mis-mapped** for the missing-file path.

## 4. Still unknown

1. **No TA was successfully loaded**, so the EXEC "golden path" (TA response `0xAA` + payload)
   could **not** be exercised. Nothing shows what a *successful* `EXEC_CMD` returns.
2. **Which TA/path is expected** — `/vendor/firmware_mnt/image/` is `Permission denied` to the
   `shell` uid, so the TA inventory could not be listed from the host; `GateServiced`
   (root) can read it. Needed: a root shell (or `adb root`) to enumerate `.mbn` files, or the
   vendor firmware package, then re-run `LOAD_TA` against a real signed TA.
3. **Why LOAD_TA fails at 12292/12298** (`load_app`/`run_load_ta`) is unconfirmed — plausibly the
   missing `qseeproxydaemon` / missing QSEE listener, but not proven.
4. **The project's own Python scripts could not be executed as-is** (`gate_protocol_test_v2.py
   conn`, `gate_oracle`, etc.) because they hard-require a host-reachable
   `127.0.0.1:8341`; the WSL→Windows-loopback path is unavailable. My probe reuses their exact
   `send_packet` wire format, and their classification would behave as follows under the
   measured semantics: `conn` (UNLOAD_TA) → `"unload ta succeed"` ✅ OK; any EXEC probe →
   `resp is None` → their "timeout" path ✅ (correct); **never** their `len(resp)==0` "CRASH"
   branch, because the server **holds the connection open** rather than closing it.
   To run them unmodified, a host-side relay into the device (or `adb root`+native adb) is needed.
5. **Long-run stability / concurrency** of the service under repeated EXEC traffic was not
   tested (single-shot probes only, deliberately).
6. **Unaudited device binaries** `/data/local/tmp/{gate_probe,gate_proto_probe,gate_cmd_enum,
   gate_ta_load}` from an earlier session were **not run** (unknown provenance / not in the
   approved script set).

## 5. Device state after

```
getprop sys.boot_completed  -> 1
ps -A | grep -i GateServiced -> root 1792 1 ... S GateServiced      (SAME pid, still alive)
netstat -tlnp | grep 8341   -> tcp 0 0 0.0.0.0:8341 0.0.0.0:* LISTEN
/proc/1792/status CapEff    -> 000001ffffffffff
qseeproxydaemon             -> still absent
```
- **GateServiced never crashed or restarted** — pid 1792 before and after all probes.
- **No connection resets, no tombstones, no error responses other than the logged codes.**
- Only residual state: normal client-side `TIME_WAIT` sockets to `:8341` (kernel housekeeping).
- WSL-side/device-side scratch (`.greq`, `.gresp`, calibration listeners on 9902–9905,
  `adb forward`/`reverse`, local echo server) were cleaned up after the run.

**Bottom line:** contradiction (a) is a *channel* confusion (logcat code vs wire silence — the
wire rule is "response = success, timeout = error"); contradiction (b) is a *domain* confusion
(kernel process CapEff vs protocol command vocabulary). No exploit was run; the device is healthy.
